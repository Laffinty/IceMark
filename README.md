# IceMark

IceMark 是一个基于 Win32 的 CPU 算力测评工具。它用一个复现 Transformer 推理访问特征的合成内核去压测处理器，跑完一组测量后给出 0–100 的评分。

评分之前会先做一次可信度自检：如果内核自己没跑通、跑出了 NaN，或者测出来的带宽和机器真实访存能力对不上，工具会拒绝出分并说明原因，而不是给一个看起来很精确的数字。

> IceMark is a Win32 CPU capability benchmark. It stresses the processor with a synthetic kernel that reproduces the memory-access and compute pattern of transformer inference, then scores the result out of 100. Before scoring it runs a validity self-check: if the kernel did not execute cleanly, produced NaN, or reported a bandwidth inconsistent with the machine's actual memory throughput, the tool withholds the score and says why instead of printing a precise-looking number.

## 构建与运行

需要 CMake ≥ 3.15 和支持 C++17 的编译器，无外部依赖。

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release
./build/Release/icemark.exe
```

不指定 `CMAKE_BUILD_TYPE` 时会自动回落到 Release——一个默认构建成 `-O0` 的测速工具测的是编译器，不是 CPU。

GUI 是默认入口。命令行模式：

```bash
icemark --cli --profile standard --repeats 5 --out report.txt
```

| 选项 | 说明 |
|---|---|
| `--cli` | 不启动 GUI，直接跑完整测量 |
| `--profile quick\|standard\|deep` | 模型规模，决定权重大小与总耗时 |
| `--repeats N` | 每个采样点的最少重复次数（低于 3 会被抬到 3） |
| `--threads N` | 线程上限，默认使用全部逻辑核 |
| `--out <文件>` | 把报告写入 UTF-8 文件 |
| `--no-int8` | 跳过 INT8 对比 |

环境变量 `NO_GUI=1` 等价于 `--cli`。

## 界面

- **机器信息**：CPU 型号、物理核 / 逻辑核、指令集、内存
- **配置行**：模型规模、重复次数、线程上限、是否测 INT8；开始 / 停止 / 导出 CSV
- **进度条**：当前阶段实时更新，测量在后台线程运行，界面不阻塞，随时可取消
- **综合评分**：总分、置信度徽章、五个子项的分条
- **四张曲线**：算力随批量的变化、多线程扩展性、上下文衰减、INT8 加速比，带误差棒
- **状态栏**：自检读数——实测带宽与访存参考的比值、NaN/Inf 计数、最大采样噪声

## 测量协议

**算力标定**在单线程下跑，每线程 token 数 M 从 1 递增到 32。M 越大，每个权重元素被复用的次数越多，算术强度越高，工作负载会自己穿过 Roofline 的拐点。工具报告 M=1（纯带宽受限）和峰值 M（计算受限）两端，读数就是单核算力。

**多线程扩展性**测量满载线程数下的加速比。一路带宽受限的负载不可能线性扩展，这本身就是有意义的结果，不是缺陷。

**解码**按几何阶梯推进上下文长度，上限取到 KV-Cache 流量与权重流量等量的量级为止——再小的上下文下 KV 占比不足 1%，测出来的其实是权重而不是 KV，衰减曲线会被完全淹没。

**INT8 对比**只量化权重，KV-Cache 保持 FP32。这与真实推理系统的做法一致，因此随着上下文增长、KV 占比上升，加速比会从接近 4× 收敛到接近 1×。收敛本身就是正确行为的证据。

**采样**每个点至少重复三次，取中位数并用 MAD 度量离散度；离散度不达标时继续采样（上限 12 次或时间预算耗尽），并剔除 3 倍稳健标准差之外的离群点。每个采样内部会连续跑多趟，直到累计约 150ms，让调度抖动被摊薄而不是主导结果。测量前先做一次约 300ms 的空转把频率拉到稳态——冷启动的第一次循环是在调频器停泊的频率上跑的，实测会低到 4 GB/s，而稳态是 16 GB/s。

## 评分模型

五个子项加权成总分：

| 子项 | 权重 | 依据 |
|---|---|---|
| 单核算力（FP32） | 30% | 峰值 GFLOP/s，跨峰值 M 取 |
| 单核内存带宽 | 25% | 顺序读带宽 |
| 多线程扩展性 | 20% | 满载线程数下的加速比 |
| 上下文衰减一致性 | 15% | 实测衰减比 vs 字节模型预测比 |
| 量化收益（INT8） | 10% | 实测加速比 vs 字节模型上限 |

前两项是**绝对量**，用对数锚定归一到 0–100（CPU 性能跨代是指数差异，线性标定会把所有真实机器压在 10 分以下）。锚点区间是架构推算的估计值，不是对其它机器的实测；超出区间时会在读数里标出来。

后三项不设锚点，而是**跟字节模型对照**：模型预测的上下文衰减倍数、量化能带来的加速上限，都可以直接从权重和 KV 的字节数算出来。实测贴着模型走就满分，偏离越远扣得越多。这样打分的是机器的行为是否符合它应该有的行为，而不是跟一堆拍脑袋的曲线比。

字节模型是一阶近似，它假设所有字节都以同样速率流出，但 KV-Cache 是跨 `ctx` 个离散行的 gather 读，大上下文下要多付带宽。健康机器因此会稳定地超出模型几倍，所以衰减一致性这一项留了容差带；偏离再多才扣分。实测到的大上下文带宽明显低于小上下文，就是这个 gather 代价的直接证据。

**总分与置信度是两个独立信号**。总分表示机器能力，置信度表示这次测量有多可靠，二者分开显示而不是揉成一个数字——否则某一个采样点偶然抖动，就会让两次跑同一台机器的总分凭空差出好几分，而实际上每个子项都只差 1 分以内。

**可信度闸门**分两级：

- **硬失败**（不出分，只给原因）：实测带宽与访存参考的比值超出 0.20×–1.35×、AVX2 内核与标量参考内核结果不一致、出现 NaN/Inf、内存不足以完成测量
- **软惩罚**（照常出分，但降低置信度并轻微下调总分）：采样离散度过高、上下文长度受内存限制。离散度超过 35% 时置信度降到 0.4 以下，此时拒绝出分——那已经基本没有信号了

**内存安全**：解码段会分配每线程数百 MB 的 KV-Cache。工具在跑之前按可用内存（不是总量）算预算，分配之前再复查一次并按需缩短上下文阶梯，内存真不够时给出可操作的提示而不是让进程崩掉。

## 架构

| 模块 | 职责 |
|---|---|
| `model` | 模型形状、精度枚举、三档规模预设、参数量与字节账 |
| `weights` | 逐层独立播种的确定性 LCG 权重生成，可并行且与线程数无关 |
| `kernel` | 推理内核：RMSNorm、QKV/输出投影 GEMM、因果注意力、KV-Cache 解码、门控 FFN、AVX2/FMA 与标量两套点积（运行时 CPUID 分派） |
| `cpu` | 拓扑与指令集检测（含物理核、AMX、OSXSAVE 门控）、内存总量与可用量 |
| `harness` | 测量协议：自检、重复采样、线程/上下文阶梯、指标定义 |
| `scoring` | 锚定表、子项评分、可信度判定 |
| `gui` | Win32 单窗口仪表板，后台线程 + `PostMessage` 回主线程 |

AVX2 只在一个单独的编译单元里生成（`-mavx2 -mfma` / `/arch:AVX2`），并在运行前用 CPUID 检查确认支持，因此生成的二进制在任何 x86-64 机器上都能安全加载。启动时会交叉校验两套点积的输出是否一致。

## 局限性

- 内核是合成的，不替代 llama.cpp / ONNX Runtime 之类的生产运行时；绝对数值不可与它们比较
- 分数反映的是**标量 / AVX2 FP32** 能力，不是 AVX-512 或 AMX 的算力；检测到的指令集会在界面上单独列出
- 锚点表是架构推算的估计区间，不是标定过的测量数据库，跨机器比较时请把它当作量级参考而非精确排名
- 测量期间机器上的其它负载会直接进入结果，请保持空闲
